# action space notes

## 1. action을 어떻게 정의할 것인가

연구계획서 기준으로 action은 크게 두 방식이 가능합니다.

### 방식 A. 작업-설비 쌍 직접 선택
- action = `(job_i, machine_m)`
- 장점:
  - 병렬 이기종 설비 문제를 가장 직접적으로 표현 가능
  - 설비 가능 여부 제약을 붙이기 쉬움
  - action masking이 자연스럽게 동작
- 단점:
  - 후보 수가 `남은 작업 수 x 현재 가용 설비 수`만큼 늘어남

### 방식 B. 설비별 다음 작업 선택
- action = `machine_m에 넣을 다음 작업 job_i`
- 장점:
  - 현업 설명에는 더 직관적일 수 있음
  - 특정 설비 관점 정책을 만들기 쉬움
- 단점:
  - 여러 설비가 동시에 비는 상황 처리 로직을 따로 설계해야 함

## 2. 현재 스켈레톤의 선택

현재 스켈레톤은 방식 A를 채택합니다.

- 이유 1: 초기 구현이 가장 단순함
- 이유 2: 하드 제약 마스킹을 붙이기 쉬움
- 이유 3: 연구계획서의 "작업을 어느 설비에 배정할지"를 직접 표현 가능

config 키:

```yaml
action_space:
  mode: job_machine_pair
```

## 3. 나중 확장

필요하면 `machine_then_job` 모드도 확장할 수 있습니다.
하지만 초기 스켈레톤은 `job_machine_pair` 하나만으로도 충분합니다.
